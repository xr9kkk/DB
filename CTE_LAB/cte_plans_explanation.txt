Объяснение планов из cte_results.txt
====================================

В файле cte_results.txt находятся три плана:

1. Запрос с оправданным CTE.
2. Тот же запрос без CTE.
3. Пример, где CTE не оправдано.


1. Оправданный CTE
==================

Задача запроса:

Выбрать названия клубов, которые:

- участвовали в двух и более соревнованиях;
- имеют спортсменов с наивысшим разрядом.

В запросе используются два CTE:

max_rank_clubs
--------------

Этот CTE находит клубы, в которых есть спортсмен с наивысшим разрядом.

Наивысший разряд определяется так:

NOT EXISTS (
    SELECT 1
    FROM Rank_title rt2
    WHERE rt2.previous_rank_id = rt.rank_title_id
)

То есть у текущего разряда нет следующего разряда, который ссылался бы на него как на previous_rank_id.

clubs_with_two_tournaments
--------------------------

Этот CTE находит клубы, которые участвовали минимум в двух турнирах.

Так как клуб может быть записан в матче и как club1_id, и как club2_id, запрос сначала объединяет оба столбца:

SELECT club1_id AS club_id, tournament_id FROM Match
UNION ALL
SELECT club2_id AS club_id, tournament_id FROM Match

После этого строки группируются по club_id, и остается только те клубы, у которых:

COUNT(DISTINCT tournament_id) >= 2

Почему CTE здесь оправдано
--------------------------

CTE оправдано не потому, что оно ускоряет запрос, а потому что разделяет задачу на понятные смысловые части:

- отдельно клубы с максимальным разрядом;
- отдельно клубы с участием в двух и более турнирах;
- в основном запросе остается только соединить эти два набора с Club.

Такой запрос легче читать, проверять и объяснять.

План выполнения
---------------

Итоговые показатели:

- Execution Time: 53.965 ms
- Planning Time: 3.069 ms
- Результат: 363 строки
- Buffers: shared hit=4993

Главный верхний узел:

Sort
  -> Nested Loop
       -> Merge Join
       -> Index Scan using club_pkey on club

PostgreSQL сначала получает подходящие club_id, затем для каждого найденного club_id берет название клуба через индекс club_pkey.

Поиск клубов с наивысшим разрядом
---------------------------------

В плане эта часть начинается с:

Unique
  -> Gather Merge
       -> Sort
            -> HashAggregate
                 -> Hash Join

Внутри PostgreSQL:

1. Параллельно читает таблицу Rank:

Parallel Seq Scan on rank
actual rows=165316.50 loops=2

Так как loops=2, таблица Rank обрабатывалась двумя процессами: основным процессом и одним worker.

2. Читает Rank_title и через Hash Anti Join находит разряды, у которых нет следующего разряда:

Hash Anti Join
actual rows=3 loops=2

Это значит, что найдено 3 наивысших разряда.

3. Соединяет Rank с найденными наивысшими разрядами.

После соединения получается:

actual rows=4802 loops=2

То есть найдено примерно 9604 записей Rank с наивысшими разрядами.

4. Соединяет эти записи со спортсменами Athlete, чтобы получить club_id спортсмена.

5. Через HashAggregate, Sort и Unique убирает повторы club_id.

В результате CTE max_rank_clubs дает список клубов, где есть хотя бы один спортсмен с наивысшим разрядом.

Поиск клубов с двумя и более турнирами
--------------------------------------

В плане эта часть:

GroupAggregate
  -> Sort
       -> Append
            -> Seq Scan on match
            -> Seq Scan on match match_1

PostgreSQL дважды читает Match:

- первый раз берет club1_id;
- второй раз берет club2_id.

Каждый проход вернул 10723 строки, потому что по одной строке было отброшено из-за NULL:

Rows Removed by Filter: 1

После UNION ALL получилось:

21446 строк

Затем выполняется сортировка:

Sort Method: quicksort
Memory: 1271kB

И после этого GroupAggregate считает количество разных tournament_id по каждому club_id.

Фильтр:

COUNT(DISTINCT tournament_id) >= 2

оставил:

actual rows=382

То есть 382 клуба участвовали минимум в двух турнирах.

Соединение двух наборов
-----------------------

Два набора club_id соединяются через Merge Join:

Merge Join
Merge Cond: a.club_id = match.club1_id
actual rows=363

Это значит, что итоговых клубов, которые одновременно:

- имеют спортсмена с наивысшим разрядом;
- участвовали минимум в двух турнирах;

получилось 363.

После этого Nested Loop делает 363 обращения к таблице Club по первичному ключу:

Index Scan using club_pkey on club c
Index Searches: 363

В конце результат сортируется по названию клуба:

Sort Key: c.name
Sort Method: quicksort
Memory: 25kB


2. Тот же запрос без CTE
========================

Второй запрос делает то же самое, но вместо CTE использует подзапросы в JOIN.

Итоговые показатели:

- Execution Time: 50.277 ms
- Planning Time: 0.437 ms
- Результат: 363 строки
- Buffers: shared hit=4990

Главное наблюдение
------------------

План почти полностью совпадает с первым:

- тот же Sort сверху;
- тот же Nested Loop;
- тот же Merge Join;
- тот же поиск клубов с максимальным разрядом через Hash Anti Join;
- тот же Append из двух проходов по Match;
- тот же GroupAggregate;
- тот же Index Scan по club_pkey.

Это показывает, что PostgreSQL встроил CTE в основной запрос и не стал материализовать его как отдельную временную таблицу.

Именно поэтому CTE-версия и версия без CTE имеют одинаковую структуру плана.

Разница во времени
------------------

CTE:

53.965 ms

Без CTE:

50.277 ms

Разница:

53.965 - 50.277 = 3.688 ms

Эта разница небольшая. Она не означает, что CTE принципиально хуже. Для таких планов небольшие колебания времени нормальны: они могут зависеть от состояния кэша, запуска worker-процесса и текущей нагрузки.

Главный вывод:

CTE здесь оправдано по читаемости, а не по ускорению. При этом план выполнения остается таким же, как у варианта без CTE.


3. Неоправданное CTE
====================

Третий запрос:

WITH sorted_athletes AS (
    SELECT last_name, first_name, middle_name, height
    FROM Athlete
)
SELECT last_name, first_name, middle_name
FROM sorted_athletes
ORDER BY height DESC
LIMIT 3;

Задача:

Выбрать трех самых высоких спортсменов.

План выполнения
---------------

Итоговые показатели:

- Execution Time: 16.071 ms
- Planning Time: 0.091 ms
- Результат: 3 строки
- Buffers: shared hit=964

План:

Limit
  -> Sort
       -> Seq Scan on athlete

PostgreSQL полностью читает таблицу Athlete:

Seq Scan on athlete
actual rows=72087

Затем сортирует строки по height DESC:

Sort Key: athlete.height DESC
Sort Method: top-N heapsort
Memory: 25kB

Так как нужен только LIMIT 3, PostgreSQL использует top-N heapsort. Это специальный способ сортировки, при котором не нужно полностью сортировать все 72087 строк. Достаточно держать в памяти только несколько лучших строк.

После этого Limit возвращает 3 строки.

Почему CTE не оправдано
-----------------------

CTE sorted_athletes ничего полезного не делает:

- не упрощает сложную логику;
- не используется повторно;
- не содержит агрегации;
- не содержит рекурсии;
- не отделяет важный смысловой этап;
- просто копирует выборку из Athlete.

PostgreSQL фактически встроил этот CTE в основной запрос, поэтому в плане нет отдельного узла CTE Scan.

Более правильный вариант без CTE:

SELECT last_name, first_name, middle_name
FROM Athlete
ORDER BY height DESC
LIMIT 3;

Он короче, понятнее и дает тот же план выполнения.


Общий вывод
===========

В первых двух планах CTE оправдано: оно разбивает сложный запрос на две понятные части, но не меняет план выполнения. PostgreSQL выполняет CTE-вариант почти так же, как вариант с подзапросами.

Это хороший пример для лабораторной:

- CTE улучшает читаемость;
- CTE не ухудшает план;
- вариант без CTE дает такой же результат и практически такой же план.

Третий план показывает обратную ситуацию. CTE используется для простой выборки из Athlete, не дает никакой пользы и только делает SQL длиннее. Поэтому такое CTE не оправдано полностью.
