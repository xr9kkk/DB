Общие термины
=============

cost
----

Это оценка PostgreSQL до выполнения запроса. Например:

cost=41240.27..41961.14

Первое число - стоимость получения первой строки, второе - стоимость получения всех строк. Это не миллисекунды, а условные единицы оптимизатора.


actual time
-----------

Это реальное время выполнения узла. Например:

actual time=336.505..349.649

Первое число - когда узел начал отдавать строки, второе - когда закончил.


rows
----

rows в cost-части - ожидаемое количество строк.
rows в actual-части - фактическое количество строк.

Например:

rows=72087 в оценке и rows=35410 фактически.

Если оценки отличаются от реальности, план может быть неидеальным.


loops
-----

Сколько раз узел выполнялся. Для параллельных планов loops часто показывает работу нескольких процессов. Например loops=2 обычно означает лидер + 1 worker.


Buffers: shared hit
-------------------

Страницы, прочитанные из shared buffers, то есть из памяти PostgreSQL. В планах нет shared read, значит физического чтения с диска не видно.


temp read / temp written
------------------------

Например:

temp read=5472 written=5520

Это временные блоки, которые PostgreSQL записывал и читал во временные файлы. Обычно появляется, когда сортировка или хэш-таблица не помещается в work_mem.

Это важный признак: запрос уже достаточно тяжелый, и увеличение work_mem может изменить план или ускорить выполнение.

6. Parallel Hash
----------------

План:

Batches: 8

Это важный узел.

PostgreSQL строит параллельную хэш-таблицу для левой части Anti Join. Batches: 8 означает, что хэш-таблица не поместилась целиком в память и была разбита на 8 частей. Поэтому появились временные файлы.

Если бы work_mem был больше, возможно, batches было бы меньше или 1, и запрос мог бы выполниться быстрее.

8. Parallel Hash Right Anti Join
--------------------------------

План:

Parallel Hash Right Anti Join
Hash Cond:
  r_prev.athlete_id = a.athlete_id
  r_prev.rank_title_id = rt.previous_rank_id
actual rows=27305 loops=2

В SQL написано NOT EXISTS. PostgreSQL преобразовал его в Anti Join.

Anti Join оставляет только те строки, для которых не найдено совпадение.

В данном плане он называется Right Anti Join, потому что оптимизатор поменял стороны соединения. Логика та же:

оставить спортсмена с текущим разрядом, если в Rank не найден предыдущий разряд этого же спортсмена.

В сумме найдено:

27305 * 2 = 54610 строк-нарушений.

Это еще не уникальные спортсмены. Один спортсмен может иметь несколько нарушений.

2. Sort с top-N heapsort
------------------------

План:

Sort Key: height DESC

actual rows=3

Это ключевой плюс варианта с LIMIT.

PostgreSQL видит LIMIT 3 и понимает, что полная сортировка всех 72087 строк не нужна. Нужно найти только 3 максимальных значения.

Поэтому используется top-N heapsort:

- PostgreSQL проходит по всем строкам;
- в памяти держит только небольшой набор лучших строк;
- память всего 25kB;
- временные файлы не используются.

Сравнение вариантов запроса 41
------------------------------

Вариант EXTRACT:

- Execution Time: 64.972 ms
- Параллельный план.
- Фильтр: EXTRACT(year FROM assignment_date) = 2024.
- Результат: 24006 строк.
- Buffers: shared hit=3727.

Вариант диапазона дат:

- Execution Time: 39.440 ms
- План без параллельности.
- Фильтр: assignment_date >= '2024-01-01' AND assignment_date < '2025-01-01'.
- Результат: 24006 строк.
- Buffers: shared hit=2750.

Разница:

64.972 - 39.440 = 25.532 ms.

Диапазонный вариант быстрее примерно на 39%.

Это особенно показательно: даже без параллельности диапазонный вариант быстрее параллельного EXTRACT-варианта.

Главные причины:

1. EXTRACT вычисляет функцию для каждой строки Rank.
2. Диапазон дат использует простые сравнения.
3. Диапазонный вариант читает меньше buffers.
4. Диапазонный вариант лучше подходит под обычный индекс по assignment_date.

Рекомендация:

Использовать диапазон:

WHERE r.assignment_date >= DATE '2024-01-01'
  AND r.assignment_date < DATE '2025-01-01'

а не:

WHERE EXTRACT(YEAR FROM r.assignment_date) = 2024

Общий вывод
===========

После добавления данных и сбора статистики различия стали более заметными.

Для запроса 48 лучше вариант без рекурсии. Он быстрее, потому что PostgreSQL смог построить параллельный план. Рекурсивный вариант возвращает тот же результат, но выполняется дольше.

Для запроса 45 однозначно лучше ORDER BY height DESC LIMIT 3. PostgreSQL использует top-N heapsort и держит в памяти только 3 лучших строки. Вариант с ROW_NUMBER() приводит к оконной функции и внешней сортировке через временный файл.

Для запроса 41 лучше диапазон дат. Он быстрее даже без параллельности, потому что не вычисляет EXTRACT для каждой строки и лучше совместим с индексом по assignment_date.
