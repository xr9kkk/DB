1. ЧТО РЕАЛИЗОВАНО

Пользователь             Пароль   Назначение
lab1_admin              admin    DBA: SUPERUSER, CREATEDB, CREATEROLE.
lab1_analyst            123      Чтение справочников, клубов, турниров, матчей.
lab1_hr_user            123      Кадровик: чтение, добавление, изменение employee.
lab1_events_user        123      Регистратор: добавление/изменение match, tournament.
lab1_delegate           123      Посредник для демонстрации передачи прав.
lab1_guest              123      Получатель переданного права в демонстрации.

Группы NOLOGIN (вход под ними невозможен):
lab1_read — SELECT на country, region, city, club, rank_title, award_type,
position, gameposition, stadion, tournament, match.
lab1_hr — SELECT/INSERT/UPDATE на employee и USAGE на его SERIAL-последовательность.
lab1_events — INSERT/UPDATE на match, tournament и USAGE на их последовательности.

Вложенность:
lab1_read -> lab1_hr -> lab1_hr_user
lab1_read -> lab1_events -> lab1_events_user
lab1_read -> lab1_analyst
Стрелка означает: роль слева выдана роли справа (GRANT слева TO справа).
Поэтому кадровик и регистратор также могут читать справочники и клубы.
DELETE и DDL бизнес-пользователям не выдаются. Сведения о владельцах,
спонсорах и спортсменах им не нужны: доступа к этим таблицам нет.
Чтение зарплат необходимо кадровику, но не аналитику/регистратору.
Права действуют на всю указанную таблицу, ограничения по отдельным клубам нет.
Таблицы других лабораторных не включены в выдачу бизнес-прав.
Администратор — суперпользователь всего кластера, а не только SportsClubDB:
это соответствует требованию DBA с доступом ко всему. ALL ON DATABASE
само по себе не даёт права на все таблицы и не заменяет SUPERUSER.

2. ОТКРЫТЬ КОНСОЛЬ И ПОКАЗАТЬ АДМИНИСТРАТОРА

Открыть PowerShell:
cd 'D:\учеба\DB'
psql -X -h localhost -p 5432 -U lab1_admin -d SportsClubDB -W
Ввести пароль admin. При вводе пароля символы не отображаются.
Если psql не найден, перед запуском добавить каталог установленной версии:
$env:Path += ';C:\Program Files\PostgreSQL\18\bin'

В psql:
\pset pager off
SELECT current_database(), session_user, current_user;
\du lab1_*
\i access_lab/02_metadata.sql

Что объяснить:
pg_roles — роли и атрибуты (пароли не показывает).
pg_auth_members — членство, включая выдачу группы другой группе.
information_schema.role_table_grants — явные табличные права и is_grantable.
has_table_privilege — эффективное право, включая наследование и SUPERUSER.
Поэтому отсутствие строки для lab1_hr_user в role_table_grants не означает
отсутствия доступа: права он получает через группу.
\dp показывает ACL таблиц и последовательностей.
Default privileges в 01 относятся только к будущим объектам lab1_admin;
бизнес-права новым таблицам нужно выдавать явно по их назначению.

4. WITH GRANT OPTION И КАСКАДНЫЙ ОТЗЫВ

Под lab1_admin в psql:
\i access_lab/03_delegation.sql

Можно вместо запуска файла копировать его команды по очереди и объяснять:
а) DBA создаёт отдельную демонстрационную таблицу и выдаёт посреднику
   SELECT ... WITH GRANT OPTION.
б) SET ROLE lab1_delegate — смена текущей роли внутри сеанса администратора.
   Посредник выдаёт SELECT гостю. В метаданных видна цепочка grantor/grantee.
в) Гость успешно читает таблицу.
г) DBA выполняет:
   REVOKE GRANT OPTION FOR SELECT ON public.lab1_grant_demo
   FROM lab1_delegate CASCADE;
д) Результат проверки: delegate_still_reads = t, guest_no_longer_reads = f.
   Вторая колонка содержит именно результат has_table_privilege гостя:
   f означает, что права SELECT у него больше нет.
   Блок DO проверяет реальный отказ гостю и печатает PASS.
е) REVOKE SELECT ... FROM lab1_delegate удаляет оставшееся право посредника.
ж) Показаны CREATE ROLE, ALTER ROLE (LOGIN, пароль, CONNECTION LIMIT, NOLOGIN),
   GRANT/REVOKE членства и DROP ROLE на временной роли.
з) ROLLBACK убирает всю демонстрацию. Файл можно запускать повторно.

WITH GRANT OPTION разрешает передавать конкретное право на объект.
Обычный GRANT SELECT разрешает только чтение.
REVOKE GRANT OPTION FOR сохраняет само право SELECT у посредника.
CASCADE удаляет зависимые выдачи; независимое право из другой группы
или другой цепочки выдачи при этом сохранялось бы. Поэтому для примера
используется отдельная таблица без альтернативных прав гостя.
Без CASCADE при наличии зависимых выдач REVOKE по умолчанию (RESTRICT)
завершился бы ошибкой. WITH ADMIN OPTION относится к раздаче членства
в роли, а не к табличным привилегиям.
SET ROLE не является новым входом: session_user остаётся lab1_admin,
current_user меняется. Именно поэтому раздел 3 и автопроверки используют
также отдельные настоящие подключения под пользователями.

5. АВТОМАТИЧЕСКАЯ ПРОВЕРКА

Выйти из psql (\q), в PowerShell:
powershell -NoProfile -ExecutionPolicy Bypass -File .\access_lab\04_check.ps1

Ожидается 18 строк PASS и All 18 checks passed.
Для другой базы/порта:
powershell -NoProfile -ExecutionPolicy Bypass -File .\access_lab\04_check.ps1 -Database SportsClubDB -Server localhost -Port 5432
Каждый сценарий открывает отдельное соединение от имени проверяемой роли.
Отказ засчитывается только при ошибке недостаточных прав SQLSTATE 42501;
ошибка подключения/синтаксиса не считается успешным тестом запрета.
Тестовые транзакции откатываются. Значения SERIAL могут увеличиться:
nextval не откатывается — пропуски идентификаторов нормальны.

6. КОРОТКИЕ ОТВЕТЫ НА ЗАЩИТЕ

Зачем группы? Права назначаются должности один раз. Нового кадровика
достаточно включить в lab1_hr, а изменение прав группы применяется ко
всем её участникам. Меньше повторов и ошибок, проще аудит и увольнение.
Зачем вложенность? Общие права чтения описаны единожды в lab1_read;
две специализированные группы наследуют их и добавляют свои права.
Почему нет DELETE? Рабочие обязанности требуют ввода и исправления,
но не удаления истории. Это принцип наименьших привилегий.
Почему нужен USAGE на последовательность? SERIAL вызывает nextval;
INSERT на таблицу сам по себе права на последовательность не даёт.
Почему отзываем права PUBLIC? Каждый пользователь неявно входит в PUBLIC.
REVOKE у конкретной роли не блокирует право, полученное другим путём.
Почему нет GRANT ALL на всю схему? В ней есть персональные данные и
объекты других лабораторных; права выдаются на перечисленные объекты.
Почему больше не postgres? Первоначальное создание DBA делает postgres;
затем 01_roles.sql подключается как lab1_admin и всю настройку делает он.
Владельцы существующих таблиц не менялись, DBA получает доступ как SUPERUSER.
Можно ли удалить роль с правами? Сначала отозвать членство/права и решить
вопрос владения объектами; DROP ROLE с зависимостями будет отклонён.

7. УСТАНОВКА НА ДРУГОМ СЕРВЕРЕ

Нужна существующая спортивная база с таблицами public из createTable.sql.
Имена ролей lab1_* должны быть свободны во всём кластере.
psql -X -h localhost -U postgres -d SportsClubDB -W -f .\access_lab\01_roles.sql
После создания администратора скрипт сам переключается на него.
Изменяются ACL перечисленных таблиц и CREATE схемы public для PUBLIC;
это влияет на тех, кто раньше получал эти права через PUBLIC.
Скрипт не удаляет таблицы и не меняет их данные.
В исходном CREATE INSERT SELECTS/createTable.sql Match расположен до
Tournament: для создания базы с нуля нужно сначала создавать Stadion,
затем Tournament, затем Match. Исходный файл содержит DROP TABLE CASCADE;
не запускайте его поверх текущей базы ради этой лабораторной.
