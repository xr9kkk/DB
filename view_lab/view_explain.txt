ОТЧЕТ ПО ПРЕДСТАВЛЕНИЯМ

В работе рассматривались обычные представления и материализованное
представление PostgreSQL. По планам выполнения видно, как оптимизатор
обрабатывает разные виды представлений и чем они отличаются по поведению.

1. Обычное представление с оконными функциями

Было создано представление v_athlete_rank_stats. Оно объединяет данные
спортсменов, клубов и разрядов, а также рассчитывает оконные функции:

- ROW_NUMBER() OVER (PARTITION BY a.club_id ORDER BY a.birth_date)
- COUNT(*) OVER (PARTITION BY a.club_id)

Запрос к этому представлению:

SELECT *
FROM v_athlete_rank_stats
WHERE age_rank_in_club <= 3;

В плане выполнения присутствуют узлы Subquery Scan и WindowAgg:

Subquery Scan on v_athlete_rank_stats
  -> WindowAgg
       Filter: row_number() <= 3

Это показывает, что представление не было полностью преобразовано в простой
запрос. PostgreSQL должен сначала выполнить соединения таблиц, отсортировать
данные, вычислить оконные функции, а затем применить фильтр по
age_rank_in_club.

В плане также видно:

Rows Removed by Filter: 326464
Execution Time: 412.798 ms

Это означает, что была обработана большая часть строк, а затем большинство из
них было отброшено фильтром. Следовательно, представления с оконными функциями
могут быть дорогими, потому что фильтрация не всегда может быть выполнена до
расчета оконных выражений.

Вывод: обычное представление не хранит данные, а является сохраненным SQL-
запросом. При обращении к нему данные вычисляются заново. Если внутри
представления есть оконные функции, сортировки или другая сложная логика,
оптимизатор не всегда может упростить план выполнения.

2. Простое обычное представление с агрегацией

Было создано представление v_club_athlete_count. Оно считает количество
спортсменов в каждом клубе:

SELECT c.club_id,
       c.name AS club_name,
       COUNT(a.athlete_id) AS athlete_count
FROM Club c
         LEFT JOIN Athlete a ON c.club_id = a.club_id
GROUP BY c.club_id, c.name;

Запрос к представлению:

SELECT *
FROM v_club_athlete_count
WHERE athlete_count > 5;

В плане выполнения видно:

HashAggregate
  Group Key: c.club_id
  Filter: count(a.athlete_id) > 5

Фильтр по athlete_count был применен после группировки как условие над
агрегатной функцией. По смыслу это соответствует HAVING COUNT(a.athlete_id) > 5.

Время выполнения:

Execution Time: 18.119 ms

Это значительно быстрее, чем запрос с оконными функциями. Такое поведение
показывает, что простые представления PostgreSQL может хорошо встроить в общий
план выполнения запроса.

Вывод: простые обычные представления обычно не ухудшают план выполнения. Они
удобны для повторного использования SQL-логики, но сами по себе не ускоряют
запросы, так как результат не хранится физически.

3. Материализованное представление

Также использовалось материализованное представление mv_athlete_awards. Оно
хранит заранее рассчитанную информацию о наградах спортсменов:

- общее количество наград;
- количество различных типов наград;
- дату последней награды.

Запрос к материализованному представлению:

SELECT *
FROM mv_athlete_awards
WHERE total_awards > 2;

План выполнения:

Seq Scan on mv_athlete_awards
  Filter: total_awards > 2
Execution Time: 2.872 ms

PostgreSQL просто читает уже сохраненный результат из материализованного
представления. Ему не нужно заново выполнять соединения таблиц, группировку и
агрегатные функции.

Для сравнения был выполнен аналогичный запрос напрямую к базовым таблицам.
В плане появились более сложные операции:

GroupAggregate
Incremental Sort
Nested Loop
Merge Left Join

Время выполнения такого запроса:

Execution Time: 89.809 ms

Это намного медленнее, чем чтение из материализованного представления.

Вывод: материализованное представление может значительно ускорить тяжелые
аналитические запросы, потому что результат запроса хранится физически.

4. Устаревание данных в материализованном представлении

После добавления новой награды в таблицу Award было проверено значение в
материализованном представлении и актуальное значение в исходных таблицах.

В материализованном представлении:

total_awards = 4

В исходных таблицах:

actual_award_count = 5

Это показывает, что материализованное представление не обновляется
автоматически при изменении данных в базовых таблицах. Для обновления нужно
выполнить команду:

REFRESH MATERIALIZED VIEW mv_athlete_awards;

Вывод: материализованное представление ускоряет чтение, но требует ручного
обновления. Пока REFRESH MATERIALIZED VIEW не выполнен, данные в нем могут быть
устаревшими.

ОБЩИЙ ВЫВОД

Обычное представление в PostgreSQL представляет собой сохраненный SQL-запрос и
не хранит данные. При обращении к нему запрос выполняется заново. Простые
представления обычно хорошо преобразуются оптимизатором и встраиваются в общий
план выполнения. Однако сложные представления, например с оконными функциями,
могут приводить к более тяжелым планам, так как часть вычислений должна быть
выполнена до фильтрации.

Материализованное представление хранит результат запроса физически. Благодаря
этому чтение из него может быть намного быстрее, особенно если исходный запрос
содержит соединения, группировки и агрегатные функции. Недостаток
материализованного представления состоит в том, что данные в нем не обновляются
автоматически. После изменения базовых таблиц требуется выполнить REFRESH
MATERIALIZED VIEW.

Таким образом, обычные представления удобны для упрощения и повторного
использования запросов, а материализованные представления полезны для ускорения
тяжелых запросов, когда допустимо периодическое обновление данных.
