Подробное объяснение двух последних планов из plans_result1.txt
===============================================================

В файле plans_result1.txt два последних плана относятся к запросу 50:

Выбрать все данные соревнования, в котором приняли участие все клубы.

Рассматриваются два варианта:

1. Через двойной NOT EXISTS.
2. Через GROUP BY, COUNT(DISTINCT ...) и сравнение с количеством всех клубов.

По результату оба запроса вернули 0 строк. Это означает, что в текущих данных нет ни одного соревнования, где приняли участие все клубы.

По данным из планов:

- Tournament: 56 турниров.
- Club: 1454 клуба.
- Match: 10724 матча.
- После соединения Match с Tournament остается 10631 строка.


1. Вариант через двойной NOT EXISTS
===================================

SQL-запрос:

EXPLAIN ANALYZE
SELECT t.*
FROM Tournament t
WHERE NOT EXISTS (
    SELECT 1
    FROM Club c
    WHERE NOT EXISTS (
        SELECT 1
        FROM Match m
        WHERE m.tournament_id = t.tournament_id
          AND (m.club1_id = c.club_id OR m.club2_id = c.club_id)
    )
);

Логика запроса
--------------

Запрос проверяет условие "в турнире участвовали все клубы" через двойное отрицание.

Внутренний NOT EXISTS проверяет, что для конкретного клуба нет матча в конкретном турнире.

Внешний NOT EXISTS проверяет, что таких клубов не существует.

То есть запрос можно прочитать так:

Выбрать турнир, для которого не существует клуба, который не участвовал в этом турнире.

Это корректная логика для задачи "все клубы участвовали".

Итог плана
----------

Основной узел:

Nested Loop Anti Join

Главные показатели:

- Execution Time: 23.189 ms
- Planning Time: 1.652 ms
- Итоговых строк: 0
- Buffers: shared hit=5293

PostgreSQL использовал Anti Join, потому что конструкция NOT EXISTS естественно преобразуется в антисоединение.
Anti Join оставляет только те строки, для которых не найдено совпадение в проверяемом наборе.

Seq Scan on tournament
----------------------

План:

Seq Scan on tournament t
actual rows=56 loops=1

Таблица Tournament маленькая, всего 56 строк. PostgreSQL просто читает ее полностью.

Это нормальное решение: для такой маленькой таблицы индекс обычно не нужен.

Materialize и Seq Scan on club
------------------------------

План:

Materialize
  -> Seq Scan on club c

Таблица Club содержит 1454 клуба, но в плане видно:

Seq Scan on club c
actual rows=55 loops=1

Это не значит, что в таблице всего 55 клубов. Общее количество клубов видно во втором плане: 1454.

Здесь PostgreSQL не стал читать все клубы, потому что выполнение остановилось раньше.
Для каждого турнира запрос ищет клуб, который не участвовал в нем.
Как только такой клуб найден, этот турнир уже не подходит, и дальше перебирать все клубы для него не нужно.

Materialize сохраняет уже прочитанные строки Club в памяти. Это нужно, чтобы при повторных проверках не обращаться к таблице Club заново.

SubPlan по таблице Match
------------------------

План:

Seq Scan on match m
Filter: ((tournament_id = t.tournament_id) AND ((club1_id = c.club_id) OR (club2_id = c.club_id)))
actual rows=0.61 loops=144
Rows Removed by Filter: 4278

Этот подзапрос проверяет, есть ли у выбранного клуба матч в выбранном турнире.

Важно, что SubPlan выполнился 144 раза.

Теоретически проверок могло быть намного больше:

56 турниров * 1454 клуба = 81424 проверки.

Но фактически PostgreSQL сделал только 144 проверки, потому что почти для каждого турнира быстро находился клуб,
который в нем не участвовал. После этого турнир сразу отбрасывался.

Именно поэтому вариант с двойным NOT EXISTS не оказался катастрофически медленным, хотя его оценочная стоимость очень большая:

cost=0.00..11320580.21

Оптимизатор закладывает возможность тяжелого сценария,
когда придется проверять много пар "турнир + клуб". Но на текущих данных срабатывает ранняя остановка.

Почему результат 0 строк
------------------------

В плане:

Nested Loop Anti Join
actual rows=0
Rows Removed by Join Filter: 88

Это означает, что PostgreSQL проверил турниры и для каждого смог найти клуб, который не участвовал в этом турнире.

Следовательно, ни один турнир не удовлетворяет условию "участвовали все клубы".

Плюсы варианта
--------------

- Логика запроса полностью соответствует задаче.
- Запрос хорошо использует раннюю остановку: если быстро найден отсутствующий клуб, турнир сразу отбрасывается.
- На текущих данных работает за 23.189 ms, что нормально.

Минусы варианта
---------------

- План потенциально тяжелый на больших данных.
- Таблица Match может просматриваться много раз.
- Условие с OR:

  m.club1_id = c.club_id OR m.club2_id = c.club_id

  усложняет использование индексов.
- Если появится турнир, в котором участвовали почти все клубы, проверок станет намного больше.


2. Вариант через GROUP BY и COUNT(DISTINCT)
==========================================

SQL-запрос:

EXPLAIN ANALYZE
SELECT t.*
FROM Tournament t
         JOIN Match m ON m.tournament_id = t.tournament_id
GROUP BY t.tournament_id
HAVING COUNT(DISTINCT
             CASE WHEN m.club1_id IS NOT NULL THEN m.club1_id
                  WHEN m.club2_id IS NOT NULL THEN m.club2_id
                 END
       ) = (SELECT COUNT(*) FROM Club);

Логика запроса
--------------

Этот вариант пытается решить задачу через подсчет.

Идея такая:

- соединить турниры с матчами;
- сгруппировать строки по турниру;
- посчитать количество разных клубов в каждом турнире;
- сравнить это количество с общим количеством клубов в таблице Club.

Если количество разных клубов в турнире равно 1454, значит в турнире участвовали все клубы.

Итог плана
----------

Основной узел:

GroupAggregate

Главные показатели:

- Execution Time: 11.742 ms
- Planning Time: 0.226 ms
- Итоговых строк: 0
- Rows Removed by Filter: 56
- Buffers: shared hit=105

Этот план быстрее первого: 11.742 ms против 23.189 ms.

Разница:

23.189 - 11.742 = 11.447 ms

Второй вариант быстрее примерно в 2 раза.

InitPlan: подсчет всех клубов
-----------------------------

План:

InitPlan 1
  -> Aggregate
       -> Seq Scan on club

PostgreSQL один раз выполняет:

SELECT COUNT(*) FROM Club

По плану:

Seq Scan on club
actual rows=1454 loops=1

Значит, всего в таблице Club 1454 клуба.

Этот результат используется в HAVING как правая часть сравнения.

Seq Scan on match
-----------------

План:

Seq Scan on match m
actual rows=10724 loops=1

PostgreSQL один раз полностью читает таблицу Match.

Это важное отличие от первого варианта. В первом варианте Match проверяется внутри SubPlan и может сканироваться много раз. Во втором варианте Match читается один раз, после чего данные агрегируются.

Seq Scan on tournament и Hash
-----------------------------

План:

Seq Scan on tournament t
actual rows=56 loops=1

Таблица Tournament маленькая, поэтому PostgreSQL читает ее полностью и строит по ней маленькую hash-таблицу:

Hash
Memory Usage: 13kB

Hash Join
---------

План:

Hash Join
Hash Cond: m.tournament_id = t.tournament_id
actual rows=10631

PostgreSQL соединяет Match и Tournament по tournament_id.

Из 10724 строк Match после соединения осталось 10631 строка. Это значит, что часть матчей не соединяется с турнирами из таблицы Tournament.

Sort
----

План:

Sort
Sort Key: t.tournament_id, CASE ...
Sort Method: quicksort
Memory: 1218kB

Перед GroupAggregate PostgreSQL сортирует данные по tournament_id и по выражению, которое используется в COUNT(DISTINCT ...).

Сортировка выполняется в памяти:

- Sort Method: quicksort
- Memory: 1218kB

Временных файлов нет. Это хорошо: сортировка не ушла на диск.

GroupAggregate
--------------

План:

GroupAggregate
Group Key: t.tournament_id
Filter: count(DISTINCT CASE ...) = (InitPlan 1).col1
Rows Removed by Filter: 56
actual rows=0

PostgreSQL группирует строки по каждому турниру. Затем для каждой группы считает COUNT(DISTINCT ...) и сравнивает результат с общим количеством клубов.

Rows Removed by Filter: 56 означает:

- было проверено 56 турниров;
- все 56 турниров не прошли условие HAVING;
- итоговый результат равен 0 строк.

Почему второй план быстрее
--------------------------

Второй вариант быстрее, потому что он обрабатывает таблицы более пакетно:

- Match читается один раз;
- Tournament читается один раз;
- Club читается один раз для подсчета общего количества;
- дальше PostgreSQL сортирует и агрегирует уже полученный набор.

В первом варианте логика более проверочная: для каждой пары "турнир + клуб" может запускаться поиск в Match.
На текущих данных ранняя остановка спасает первый вариант, но он все равно медленнее.

Важное замечание по корректности второго запроса
-----------------------------------------------

Второй запрос в текущем виде написан не совсем корректно:

CASE WHEN m.club1_id IS NOT NULL THEN m.club1_id
     WHEN m.club2_id IS NOT NULL THEN m.club2_id
END

Если club1_id не NULL, PostgreSQL берет club1_id и уже не смотрит на club2_id.

В обычном матче club1_id почти всегда заполнен. Поэтому выражение фактически считает в основном только первые клубы из матчей и не учитывает вторые клубы как отдельных участников.

То есть план быстрый, но сам SQL может давать неправильную проверку участия всех клубов.

Корректнее сначала превратить club1_id и club2_id в один общий столбец club_id, а потом считать DISTINCT.

Например:

WITH tournament_clubs AS (
    SELECT tournament_id, club1_id AS club_id
    FROM Match
    WHERE club1_id IS NOT NULL

    UNION ALL

    SELECT tournament_id, club2_id AS club_id
    FROM Match
    WHERE club2_id IS NOT NULL
)
SELECT t.*
FROM Tournament t
JOIN tournament_clubs tc ON tc.tournament_id = t.tournament_id
GROUP BY t.tournament_id
HAVING COUNT(DISTINCT tc.club_id) = (SELECT COUNT(*) FROM Club);

Такой вариант считает участников корректно: и из club1_id, и из club2_id.


Сравнение двух вариантов
========================

Вариант 1: двойной NOT EXISTS
-----------------------------

- Execution Time: 23.189 ms.
- Возвращает 0 строк.
- Использует Nested Loop Anti Join.
- Логически точно выражает условие "нет клуба, который не участвовал".
- Быстро отбрасывает турниры благодаря ранней остановке.
- Может стать дорогим, если нужно будет проверять много клубов для каждого турнира.

Вариант 2: GROUP BY и COUNT(DISTINCT)
-------------------------------------

- Execution Time: 11.742 ms.
- Возвращает 0 строк.
- Использует Hash Join, Sort и GroupAggregate.
- Быстрее на текущих данных.
- Читает Match один раз, а не запускает проверку Match много раз.
- В текущем SQL есть проблема с учетом club2_id.


Общий вывод
===========

По текущим данным оба запроса показывают, что турнира с участием всех клубов нет.

Первый вариант через двойной NOT EXISTS логически правильный и хорошо подходит для выражения условия "все клубы участвовали". Его преимущество в том, что он может рано остановить проверку турнира, если быстро найден клуб без участия. В текущем плане это видно по тому, что SubPlan выполнен только 144 раза вместо потенциальных 81424 проверок.

Второй вариант быстрее по плану выполнения: 11.742 ms против 23.189 ms. Он читает Match один раз, соединяет матчи с турнирами, сортирует строки и агрегирует их по турнирам. Для больших данных такой подход часто удобнее и стабильнее.

Но второй SQL нужно исправить, потому что текущий CASE учитывает только один клуб из матча. Если исправить его через UNION ALL по club1_id и club2_id, получится более корректный агрегатный вариант.

Итоговая рекомендация:

- для строгой и понятной проверки можно оставить вариант с двойным NOT EXISTS;
- для более производительного агрегатного подхода лучше использовать исправленный вариант через UNION ALL и COUNT(DISTINCT club_id).
