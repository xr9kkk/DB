Объяснение планов из window_results.txt
=======================================

В файле window_results.txt находятся четыре плана:

1. Запрос 45 без оконной функции.
2. Запрос 45 с оконной функцией ROW_NUMBER().
3. Запрос 51 без оконной функции.
4. Запрос 51 с оконной функцией RANK().

Смысл лабораторной:

- показать случай, где оконная функция не лучше обычного запроса;
- показать случай, где оконная функция лучше обычного запроса.


1. Запрос 45 без оконной функции
================================

Задача:

Выбрать фамилии, имена, отчества трех самых высоких спортсменов.

SQL:

SELECT last_name, first_name, middle_name
FROM Athlete
ORDER BY height DESC
LIMIT 3;

Итог плана:

- Execution Time: 15.830 ms
- Planning Time: 0.840 ms
- Результат: 3 строки
- Buffers: shared hit=964

План:

Limit
  -> Sort
       -> Seq Scan on athlete

PostgreSQL полностью читает таблицу Athlete:

Seq Scan on athlete
actual rows=72087

Затем сортирует спортсменов по росту:

Sort Key: height DESC
Sort Method: top-N heapsort
Memory: 25kB

Самый важный момент здесь - Sort Method: top-N heapsort.

Так как запросу нужны только первые 3 строки, PostgreSQL не сортирует полностью все 72087 спортсменов. Он держит в памяти только небольшой набор лучших строк. Поэтому сортировка занимает всего 25kB памяти и выполняется быстро.

После сортировки узел Limit возвращает 3 строки.

Вывод по плану:

Для задачи "выбрать top-3" обычный ORDER BY + LIMIT подходит очень хорошо. PostgreSQL использует оптимизированную top-N сортировку.


2. Запрос 45 с оконной функцией
===============================

SQL:

SELECT last_name, first_name, middle_name
FROM (
    SELECT *, ROW_NUMBER() OVER (ORDER BY height DESC) AS rn
    FROM Athlete
) t
WHERE rn <= 3;

Итог плана:

- Execution Time: 28.276 ms
- Planning Time: 0.100 ms
- Результат: 3 строки
- Buffers: shared hit=961
- Temp: read=317, written=360

План:

Subquery Scan on t
  -> WindowAgg
       -> Sort
            -> Seq Scan on athlete

Таблица Athlete снова читается полностью:

Seq Scan on athlete
actual rows=72087

Затем данные сортируются по росту:

Sort Key: athlete.height DESC
Sort Method: external merge
Disk: 2872kB

В отличие от первого плана, здесь используется не top-N heapsort, а external merge. Это значит, что сортировка не уместилась полностью в рабочую память и PostgreSQL использовал временные файлы на диске:

temp read=317 written=360

После сортировки выполняется WindowAgg:

WindowAgg
Run Condition: row_number() OVER w1 <= 3

PostgreSQL вычисляет ROW_NUMBER() по порядку height DESC и оставляет строки, где rn <= 3.

Хотя в плане есть Run Condition, оконной функции все равно нужна отсортированная входная последовательность. Поэтому запрос тяжелее, чем простой LIMIT.

Сравнение пары 1
================

Без оконной функции:

- Execution Time: 15.830 ms
- Sort Method: top-N heapsort
- Memory: 25kB
- Временных файлов нет

С оконной функцией:

- Execution Time: 28.276 ms
- Sort Method: external merge
- Disk: 2872kB
- Есть temp read/temp written

Разница:

28.276 - 15.830 = 12.446 ms

Оконный вариант медленнее примерно в 1.8 раза.

Вывод:

Для запроса 45 оконная функция не лучше. Простая конструкция ORDER BY height DESC LIMIT 3 эффективнее, потому что позволяет использовать top-N heapsort.


3. Запрос 51 без оконной функции
================================

Задача:

Выбрать соревнование, в котором участвовало наибольшее количество клубов.

SQL-идея:

1. Посчитать количество разных клубов по каждому турниру.
2. Отдельно найти максимальное значение этого количества.
3. Выбрать турниры, у которых количество клубов равно максимуму.

Итог плана:

- Execution Time: 20.564 ms
- Planning Time: 1.418 ms
- Результат: 1 строка
- Buffers: shared hit=361

Главная особенность плана:

Один и тот же расчет количества клубов по турнирам выполняется два раза.

Это видно по двум похожим частям плана:

1. InitPlan 1:

Aggregate
  -> GroupAggregate
       -> Unique
            -> Merge Append

2. Основная часть:

GroupAggregate
  -> Unique
       -> Merge Append

InitPlan нужен, чтобы найти MAX(club_count). Основная часть нужна, чтобы получить club_count для каждого турнира и сравнить его с этим максимумом.

Как считается количество клубов
-------------------------------

В обоих местах PostgreSQL делает одно и то же:

Merge Append
  -> Sort
       -> Seq Scan on match
  -> Sort
       -> Seq Scan on match match_1

Таблица Match читается дважды:

- один проход для club1_id;
- второй проход для club2_id.

Каждый проход дает 10723 строки:

Seq Scan on match
actual rows=10723

После объединения получается 21446 строк:

Merge Append
actual rows=21446

Затем выполняется Unique:

Unique
actual rows=5947

Это нужно из-за UNION: одинаковые пары tournament_id + club_id удаляются.

После этого GroupAggregate считает количество разных клубов по турнирам.

Почему план тяжелее
-------------------

Основная проблема в том, что расчет club_count повторяется два раза:

- первый раз внутри InitPlan для MAX(club_count);
- второй раз в основной части запроса.

Из-за этого Match фактически обрабатывается дважды в полном объеме для одной и той же логики.

После нахождения подходящего tournament_id PostgreSQL соединяет результат с Tournament через Nested Loop:

Nested Loop
Join Filter: t.tournament_id = match.tournament_id
Rows Removed by Join Filter: 54

Таблица Tournament маленькая, поэтому Seq Scan on tournament дешевый, но главная стоимость уже была потрачена на повторный подсчет club_count.


4. Запрос 51 с оконной функцией
===============================

SQL-идея:

1. Один раз посчитать club_count по каждому турниру.
2. Соединить результат с Tournament.
3. Пронумеровать турниры через RANK() по убыванию club_count.
4. Оставить только rnk = 1.

Итог плана:

- Execution Time: 10.333 ms
- Planning Time: 0.179 ms
- Результат: 1 строка
- Buffers: shared hit=184

План:

Subquery Scan on tournament_rank
  -> WindowAgg
       -> Sort
            -> Hash Join
                 -> GroupAggregate
                 -> Seq Scan on tournament

Сначала PostgreSQL один раз считает club_count по турнирам.

Эта часть такая же по смыслу, как в третьем плане:

GroupAggregate
  -> Unique
       -> Merge Append
            -> Sort + Seq Scan on match
            -> Sort + Seq Scan on match match_1

Match снова читается дважды: отдельно для club1_id и club2_id. Но важно, что весь расчет выполняется один раз, а не два раза.

После GroupAggregate получается:

GroupAggregate
actual rows=57

Затем эти данные соединяются с Tournament:

Hash Join
actual rows=56

Tournament маленькая таблица:

Seq Scan on tournament
actual rows=56

После этого строки сортируются по количеству клубов:

Sort Key: count(DISTINCT match.club1_id) DESC
Sort Method: quicksort
Memory: 29kB

Сортируется всего 56 строк, поэтому сортировка очень дешевая.

Затем выполняется оконная функция:

WindowAgg
Run Condition: rank() OVER w1 <= 1

RANK() присваивает первое место турниру или турнирам с максимальным количеством клубов. Фильтр оставляет только rnk = 1.

Сравнение пары 2
================

Без оконной функции:

- Execution Time: 20.564 ms
- Buffers: shared hit=361
- Расчет club_count выполняется два раза
- Есть InitPlan для MAX(club_count)

С оконной функцией:

- Execution Time: 10.333 ms
- Buffers: shared hit=184
- Расчет club_count выполняется один раз
- RANK() выбирает максимальный результат после одной агрегации

Разница:

20.564 - 10.333 = 10.231 ms

Оконный вариант быстрее почти в 2 раза.

Вывод:

Для запроса 51 оконная функция лучше. Она позволяет не считать один и тот же агрегат дважды. Сначала строится таблица tournament_id + club_count, потом RANK() выбирает турнир с максимальным количеством клубов.


Общий вывод
===========

Запрос 45 показывает случай, где оконная функция не нужна и ухудшает план. Для top-N задачи обычный ORDER BY + LIMIT эффективнее, потому что PostgreSQL использует top-N heapsort.

Запрос 51 показывает обратную ситуацию. Оконная функция RANK() улучшает запрос, потому что заменяет повторный поиск MAX(club_count) после агрегации. Благодаря этому расчет количества клубов по турнирам выполняется один раз, а не дважды.

Итог для лабораторной:

- Оконка не лучше: запрос 45, ROW_NUMBER() против ORDER BY + LIMIT.
- Оконка лучше: запрос 51, RANK() против повторного подсчета MAX(club_count).
