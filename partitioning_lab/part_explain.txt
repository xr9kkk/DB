ОТЧЕТ ПО ПАРТИЦИОНИРОВАНИЮ

В лабораторной работе сравнивались две таблицы с одинаковыми данными:

- match_no_partition - обычная таблица;
- match_with_partition - партиционированная таблица.

Партиционированная таблица была разбита по диапазонам значения match_date:

- match_2024 - матчи с 2024-01-01 до 2025-01-01;
- match_2025 - матчи с 2025-01-01 до 2026-01-01;
- match_2026 - матчи с 2026-01-01 до 2027-01-01;
- match_other - DEFAULT-партиция для дат, которые не попали в явные диапазоны.

Изначально в скрипте использовалась команда:

CREATE TABLE match_with_partition (LIKE Match INCLUDING ALL)
PARTITION BY RANGE (match_date);

С ней могла возникать проблема: INCLUDING ALL переносит индексы и ограничения,
в том числе первичный ключ исходной таблицы Match. В PostgreSQL уникальный ключ
или первичный ключ на партиционированной таблице должен включать ключ
партиционирования. Исходный первичный ключ Match построен только по match_id, а
партиционирование выполняется по match_date. Поэтому такой ключ несовместим с
таблицей PARTITION BY RANGE (match_date).

Скрипт был исправлен так:

CREATE TABLE match_with_partition
(LIKE Match INCLUDING DEFAULTS INCLUDING CONSTRAINTS)
PARTITION BY RANGE (match_date);

Так копируются структура, значения по умолчанию и CHECK-ограничения, но не
переносится проблемный первичный ключ.

1. Распределение строк по партициям

После вставки данных была выполнена проверка:

SELECT tableoid::regclass AS partition_name, COUNT(*) AS row_count
FROM match_with_partition
GROUP BY tableoid::regclass
ORDER BY partition_name;

Результат:

match_2024  - 77 строк
match_2025  - 6727 строк
match_2026  - 3668 строк
match_other - 252 строки

Это показывает, что PostgreSQL физически разложил строки по отдельным
таблицам-партициям в зависимости от значения match_date.

2. Фильтр по ключу партиционирования в обычной таблице

Запрос:

SELECT COUNT(*)
FROM match_no_partition
WHERE match_date BETWEEN '2025-01-01' AND '2025-12-31';

План выполнения:

Seq Scan on match_no_partition
  Filter: match_date between 2025-01-01 and 2025-12-31
  Rows Removed by Filter: 3997
Execution Time: 0.899 ms

Обычная таблица не разбита на секции, поэтому PostgreSQL выполняет
последовательное сканирование всей таблицы. Он просматривает все строки,
оставляет 6727 строк за 2025 год, а 3997 строк отбрасывает фильтром.

Вывод: в обычной таблице фильтр по дате не позволяет пропустить физическую
часть таблицы, если нет подходящего индекса.

3. Фильтр по ключу партиционирования в партиционированной таблице

Запрос:

SELECT COUNT(*)
FROM match_with_partition
WHERE match_date BETWEEN '2025-01-01' AND '2025-12-31';

План выполнения:

Seq Scan on match_2025 match_with_partition
Execution Time: 0.743 ms

В плане видно, что PostgreSQL сканирует только партицию match_2025. Партиции
match_2024, match_2026 и match_other не читаются.

Это называется partition pruning - отсечение ненужных партиций. Так как
условие запроса задано по ключу партиционирования match_date, PostgreSQL может
заранее определить, что нужные строки за 2025 год находятся только в партиции
match_2025.

Вывод: партиционирование полезно, когда запросы часто фильтруют данные по
ключу партиционирования. В этом случае PostgreSQL может не читать лишние
части данных.

4. Фильтр не по ключу партиционирования в обычной таблице

Запрос:

SELECT COUNT(*)
FROM match_no_partition
WHERE club1_id = (SELECT club_id FROM Club WHERE name = 'Spartak' LIMIT 1);

План выполнения:

Seq Scan on match_no_partition
  Filter: club1_id = ...
  Rows Removed by Filter: 10678
Execution Time: 0.490 ms

PostgreSQL сначала находит club_id клуба Spartak через индекс по таблице Club,
а затем сканирует таблицу match_no_partition и проверяет условие club1_id для
каждой строки.

Подходящих строк найдено 46, остальные 10678 строк были отброшены фильтром.

5. Фильтр не по ключу партиционирования в партиционированной таблице

Запрос:

SELECT COUNT(*)
FROM match_with_partition
WHERE club1_id = (SELECT club_id FROM Club WHERE name = 'Spartak' LIMIT 1);

План выполнения:

Append
  -> Seq Scan on match_2024
  -> Seq Scan on match_2025
  -> Seq Scan on match_2026
  -> Seq Scan on match_other
Execution Time: 0.487 ms

Здесь PostgreSQL не может отбросить партиции, потому что таблица разбита по
match_date, а фильтр идет по club1_id. Значение club1_id не говорит, в какой
партиции по дате могут находиться строки.

Поэтому используется узел Append: PostgreSQL выполняет сканирование всех
партиций и объединяет результат.

Вывод: партиционирование ускоряет не все запросы, а прежде всего те, где
условие связано с ключом партиционирования. Если фильтр идет по другому
столбцу, PostgreSQL обычно должен проверить все партиции.

6. UPDATE с изменением ключа партиционирования

Запрос к партиционированной таблице:

UPDATE match_with_partition
SET match_date = match_date + INTERVAL '1 year'
WHERE match_date < '2026-01-01';

План выполнения:

Update on match_with_partition
  Update on match_2024
  Update on match_2025
  Update on match_other
  -> Append
       -> Seq Scan on match_2024
       -> Seq Scan on match_2025
       -> Seq Scan on match_other
Execution Time: 18.383 ms

Этот UPDATE изменяет поле match_date, то есть ключ партиционирования. Если
после изменения даты строка попадает в другой диапазон, PostgreSQL должен
переместить ее из одной партиции в другую.

Например, строка из match_2025 после прибавления одного года может попасть в
match_2026. Для партиционированной таблицы это дороже, чем обычное изменение
поля внутри одной таблицы, потому что фактически выполняется перенос строки
между физическими секциями.

Для обычной таблицы аналогичный запрос:

UPDATE match_no_partition
SET match_date = match_date + INTERVAL '1 year'
WHERE match_date < '2026-01-01';

План:

Update on match_no_partition
  -> Seq Scan on match_no_partition
Execution Time: 24.751 ms

В данном конкретном запуске обычная таблица обновилась медленнее, но это не
отменяет общего правила: изменение ключа партиционирования является дорогой
операцией, потому что может требовать перемещения строк между партициями.
Фактическое время зависит от объема данных, настроек, состояния кэша и
количества изменяемых строк.

7. Общий вывод

Партиционирование делит одну логическую таблицу на несколько физических
частей. В данной работе таблица match_with_partition была разбита по диапазону
дат match_date.

Главное преимущество партиционирования видно в запросе с фильтром по
match_date за 2025 год. Обычная таблица выполнила Seq Scan по всей таблице, а
партиционированная таблица прочитала только match_2025. Это показывает работу
partition pruning - отсечения ненужных партиций.

Однако при фильтрации по club1_id партиционирование не помогло. PostgreSQL
использовал Append и просмотрел все партиции, потому что club1_id не является
ключом партиционирования.

Также важно учитывать, что изменение ключа партиционирования может быть
дорогим. Если новое значение ключа попадает в другой диапазон, строка должна
быть перемещена в другую партицию.

Таким образом, партиционирование полезно для больших таблиц, когда запросы
часто ограничивают данные по тому же полю, по которому выполнено разбиение.
В этой лабораторной таким полем является match_date.
