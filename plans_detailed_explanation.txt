Подробное объяснение планов выполнения
======================================

Разбираются планы из файла plans_result.txt для запросов из plan_queries.sql.
В файле есть три пары запросов:

1. Запрос 48:
   - вариант без рекурсии;
   - вариант с WITH RECURSIVE.

2. Запрос 45:
   - вариант ORDER BY height DESC LIMIT 3;
   - вариант через ROW_NUMBER().

3. Запрос 41:
   - вариант с EXTRACT(YEAR FROM assignment_date) = 2024;
   - вариант с диапазоном дат assignment_date >= '2024-01-01' AND assignment_date < '2025-01-01'.


Общие обозначения в EXPLAIN ANALYZE
===================================

cost
----

Например:

cost=17313.55..17674.39

Это оценка PostgreSQL до реального выполнения запроса. Первое число - стоимость получения первой строки, второе число - стоимость получения всех строк. Это не миллисекунды, а условные единицы оптимизатора.


actual time
-----------

Например:

actual time=108.435..110.667

Это реальное время выполнения узла. Первое число - когда узел начал возвращать первые строки, второе - когда закончил.


rows
----

В плане обычно есть две оценки строк:

rows=36084 в части cost - сколько строк ожидал оптимизатор.
rows=14410 в части actual - сколько строк реально получилось.

Если оценка сильно отличается от реальности, PostgreSQL может выбрать не самый удачный план.


loops
-----

Показывает, сколько раз узел был выполнен. Если loops=1, узел выполнен один раз. Если loops больше 1, реальное суммарное время узла примерно равно actual time, умноженному на loops.


Buffers: shared hit
-------------------

Например:

Buffers: shared hit=2078

Это количество страниц, которые PostgreSQL взял из shared buffers, то есть из памяти. В этих планах нет shared read, значит чтения с диска не было. Данные уже находились в памяти, поэтому планы выполняются быстрее, чем при холодном кэше.


Planning Time
-------------

Время, которое PostgreSQL потратил на построение плана.


Execution Time
--------------

Полное время выполнения запроса. Именно его удобнее всего использовать для общего сравнения вариантов.


Запрос 48. Поиск спортсменов, которые перепрыгнули через разряд
===============================================================

Задача запроса:

Нужно найти спортсменов, у которых есть некоторый разряд, но нет предыдущего разряда из иерархии. Например, если у спортсмена есть разряд 4, а предыдущий для него разряд 3, но записи о разряде 3 нет, значит спортсмен нарушил порядок получения разрядов.


Запрос 48, вариант 1. Без рекурсии
----------------------------------

SQL-идея:

SELECT DISTINCT a.*
FROM Athlete a
JOIN Rank r ON r.athlete_id = a.athlete_id
JOIN Rank_title rt ON rt.rank_title_id = r.rank_title_id
WHERE rt.previous_rank_id IS NOT NULL
  AND NOT EXISTS (
      SELECT 1
      FROM Rank r_prev
      WHERE r_prev.athlete_id = a.athlete_id
        AND r_prev.rank_title_id = rt.previous_rank_id
  );

Итог:

Execution Time: 112.473 ms
Planning Time: 2.802 ms
Итоговых строк: 14410
Строк до DISTINCT: 21610
Buffers: shared hit=2078


1. Seq Scan on rank r
---------------------

План:

Seq Scan on rank r
rows=147612

PostgreSQL полностью читает таблицу Rank. Это таблица присвоенных разрядов. Полное чтение нужно, потому что в запросе нет условия, которое заранее ограничивает Rank по дате, спортсмену или конкретному разряду.

Реально прочитано 147612 строк. Это основная рабочая таблица для запроса.


2. Seq Scan on rank_title rt
----------------------------

План:

Seq Scan on rank_title rt
Filter: previous_rank_id IS NOT NULL
Rows Removed by Filter: 2
rows=12

Таблица Rank_title маленькая. В ней всего 14 строк. PostgreSQL читает ее целиком и отбрасывает 2 строки, у которых previous_rank_id IS NULL.

Эти 2 строки - начальные разряды. Для них нет предыдущего разряда, поэтому спортсмен не может "перепрыгнуть" предыдущую ступень.

Остается 12 разрядов, у которых предыдущий разряд есть.


3. Hash Join между Rank и Rank_title
------------------------------------

План:

Hash Join
Hash Cond: r.rank_title_id = rt.rank_title_id
actual rows=118811

PostgreSQL строит хэш-таблицу по маленькой Rank_title, а затем проходит по большой Rank и быстро ищет соответствующий rank_title_id.

После соединения остается 118811 строк. Это записи о присвоенных разрядах, для которых сам разряд имеет предыдущий разряд.

То есть дальше проверяются только такие разряды, где вообще есть что проверять.


4. Seq Scan on athlete a
------------------------

План:

Seq Scan on athlete a
rows=36084

PostgreSQL полностью читает таблицу Athlete и строит по ней хэш.

Таблица спортсменов содержит 36084 строки. Она соединяется с Rank по athlete_id, чтобы вернуть данные спортсмена.


5. Hash Join Rank + Athlete
---------------------------

План:

Hash Join
Hash Cond: r.athlete_id = a.athlete_id
actual rows=118811

Каждая запись о разряде соединяется со своим спортсменом.

Количество строк осталось 118811, потому что у каждой записи Rank есть соответствующий спортсмен.


6. Seq Scan on rank r_prev
--------------------------

План:

Seq Scan on rank r_prev
rows=147612

Таблица Rank читается второй раз. Второй экземпляр нужен для проверки: есть ли у этого же спортсмена предыдущий разряд.

PostgreSQL строит хэш по парам:

athlete_id, rank_title_id

Потом по этому хэшу будет проверяться наличие предыдущего разряда.


7. Hash Anti Join
-----------------

План:

Hash Anti Join
Hash Cond:
  a.athlete_id = r_prev.athlete_id
  rt.previous_rank_id = r_prev.rank_title_id
actual rows=21610

Это самый важный узел плана.

В SQL был NOT EXISTS. PostgreSQL преобразовал его в Hash Anti Join.

Anti Join работает так:

1. Берется строка из левой части. Здесь это спортсмен и его текущий разряд.
2. PostgreSQL ищет в правой части строку с таким же athlete_id и rank_title_id, равным previous_rank_id текущего разряда.
3. Если такая строка найдена, значит предыдущий разряд есть, спортсмен ничего не нарушил.
4. Если такая строка не найдена, строка остается в результате.

После Anti Join осталось 21610 строк. Это не уникальные спортсмены, а строки-нарушения. Один спортсмен может попасть несколько раз, если у него несколько разрядов без нужных предыдущих разрядов.


8. HashAggregate
----------------

План:

HashAggregate
Group Key: все столбцы Athlete
actual rows=14410

В запросе написано SELECT DISTINCT a.*. PostgreSQL реализует DISTINCT через HashAggregate.

Он группирует строки по всем столбцам Athlete:

athlete_id, club_id, last_name, first_name, middle_name, gender, birth_date, phone, height, weight, game_position_id.

После удаления дублей осталось 14410 уникальных спортсменов.


Вывод по варианту 1
-------------------

План логичный и достаточно эффективный для такого запроса:

- Rank читается два раза;
- Rank_title маленькая и почти не влияет на стоимость;
- NOT EXISTS выполнен через Hash Anti Join;
- DISTINCT выполнен через HashAggregate.

Главная стоимость - два полных прохода по Rank и обработка 118811 строк перед Anti Join.


Запрос 48, вариант 2. С рекурсивной CTE
---------------------------------------

SQL-идея:

WITH RECURSIVE rank_chain AS (...)
SELECT DISTINCT a.*
FROM Athlete a
JOIN Rank r ON r.athlete_id = a.athlete_id
JOIN rank_chain rc ON rc.rank_title_id = r.rank_title_id
WHERE rc.previous_rank_id IS NOT NULL
  AND NOT EXISTS (...);

Итог:

Execution Time: 106.770 ms
Planning Time: 0.396 ms
Итоговых строк: 14410
Строк до DISTINCT: 21610
Buffers: shared hit=2079


1. Recursive Union
------------------

План:

CTE rank_chain
Recursive Union
actual rows=14

Сначала PostgreSQL строит рекурсивную таблицу rank_chain.

Начальная часть:

SELECT rank_title_id, rank_title, previous_rank_id, 1 AS lvl
FROM Rank_title
WHERE previous_rank_id IS NULL

Она находит корневые разряды. Таких строк 2.

Рекурсивная часть:

SELECT rt.rank_title_id, rt.rank_title, rt.previous_rank_id, rc.lvl + 1
FROM Rank_title rt
JOIN rank_chain rc ON rt.previous_rank_id = rc.rank_title_id

Она находит следующие разряды в цепочке.

План показывает:

loops=7
итого rows=14
Maximum Storage: 33kB

Рекурсия очень дешевая, потому что Rank_title маленькая.


2. CTE Scan on rank_chain
-------------------------

План:

CTE Scan on rank_chain rc
Filter: previous_rank_id IS NOT NULL
rows=12
Rows Removed by Filter: 2

После построения иерархии PostgreSQL отбрасывает начальные разряды. Остаются те же 12 проверяемых разрядов, что и в варианте без рекурсии.


3. Hash Join Rank + rank_chain
------------------------------

План:

Hash Join
Hash Cond: r.rank_title_id = rc.rank_title_id
actual rows=118811

Этот узел делает то же, что в первом варианте делал Hash Join между Rank и Rank_title.

После соединения снова остается 118811 записей Rank, у которых разряд имеет previous_rank_id.


4. Hash Join с Athlete
----------------------

План:

Hash Join
Hash Cond: r.athlete_id = a.athlete_id
actual rows=118811

PostgreSQL читает Athlete полностью, строит хэш и соединяет со строками Rank.


5. Hash Anti Join
-----------------

План:

Hash Anti Join
Hash Cond:
  a.athlete_id = r_prev.athlete_id
  rc.previous_rank_id = r_prev.rank_title_id
actual rows=21610

Как и в первом варианте, NOT EXISTS превращен в Hash Anti Join.

Логика такая же:

оставить только те строки, для которых у спортсмена нет предыдущего разряда.


6. HashAggregate
----------------

План:

HashAggregate
actual rows=14410

SELECT DISTINCT a.* снова реализован через HashAggregate. После удаления дублей остаются те же 14410 спортсменов.


Вывод по варианту 2
-------------------

Рекурсивная CTE почти не утяжелила план, потому что справочник Rank_title маленький. Основная работа по-прежнему находится в Rank, Hash Anti Join и DISTINCT.

Этот вариант чуть быстрее по фактическому времени:

106.770 ms против 112.473 ms.

Но разница небольшая. Она может быть следствием кэша, статистики, порядка выполнения и небольших различий в оценках.


Сравнение вариантов запроса 48
------------------------------

Вариант 1:

Execution Time: 112.473 ms

Вариант 2:

Execution Time: 106.770 ms

Оба варианта возвращают:

14410 уникальных спортсменов.

Оба варианта находят:

21610 строк-нарушений до DISTINCT.

Главное отличие:

- вариант 1 сразу использует Rank_title;
- вариант 2 сначала строит рекурсивную rank_chain.

Практический вывод:

Если нужно просто проверить наличие непосредственного предыдущего разряда, вариант 1 лучше как более простой. Если нужно объяснить иерархию или использовать уровень разряда lvl, вариант 2 интереснее.

По производительности они почти одинаковые. Рекурсия не стала проблемой, потому что Rank_title маленькая.


Запрос 45. Три самых высоких спортсмена
======================================

Задача:

Нужно вывести фамилию, имя и отчество трех самых высоких спортсменов.


Запрос 45, вариант 1. ORDER BY + LIMIT
--------------------------------------

SQL:

SELECT last_name, first_name, middle_name
FROM Athlete
ORDER BY height DESC
LIMIT 3;

Итог:

Execution Time: 7.453 ms
Planning Time: 0.056 ms
Результат: 3 строки
Buffers: shared hit=484


1. Seq Scan on athlete
----------------------

План:

Seq Scan on athlete
actual rows=36084

PostgreSQL полностью прочитал таблицу Athlete. Это произошло потому, что в плане нет индекса по height, который позволил бы сразу идти от самых высоких значений.

Чтобы узнать трех самых высоких спортсменов без индекса, нужно посмотреть рост всех спортсменов.


2. Sort
-------

План:

Sort
Sort Key: height DESC
Sort Method: top-N heapsort
Memory: 25kB

Это ключевая особенность плана.

Так как в запросе есть LIMIT 3, PostgreSQL не обязан сортировать все 36084 строки полностью. Ему нужны только 3 лучшие строки.

Поэтому используется top-N heapsort.

Смысл top-N heapsort:

PostgreSQL проходит по всем строкам, но в памяти держит только небольшой набор лучших кандидатов. В данном случае ему нужно всего 3 строки, поэтому памяти потребовалось только 25kB.

Это намного дешевле полной сортировки.


3. Limit
--------

План:

Limit
actual rows=3

После сортировки PostgreSQL возвращает только первые 3 строки.


Вывод по варианту 1
-------------------

Это хороший план для задачи top-N:

- запрос простой;
- нет соединений;
- нет агрегации;
- используется top-N heapsort;
- время выполнения маленькое.

Если добавить индекс по height DESC, запрос может стать еще быстрее:

CREATE INDEX ON Athlete(height DESC);

Тогда PostgreSQL сможет читать строки уже в нужном порядке и остановиться после первых трех.


Запрос 45, вариант 2. ROW_NUMBER()
----------------------------------

SQL:

SELECT last_name, first_name, middle_name
FROM (
    SELECT *, ROW_NUMBER() OVER (ORDER BY height DESC) AS rn
    FROM Athlete
) t
WHERE rn <= 3;

Итог:

Execution Time: 10.461 ms
Planning Time: 0.082 ms
Результат: 3 строки
Buffers: shared hit=481


1. Seq Scan on athlete
----------------------

PostgreSQL снова читает всю таблицу Athlete:

actual rows=36084

Это ожидаемо: чтобы пронумеровать спортсменов по росту, нужно получить строки и отсортировать их.


2. Sort
-------

План:

Sort
Sort Key: athlete.height DESC
Sort Method: quicksort
Memory: 3057kB

Здесь используется quicksort, а не top-N heapsort.

Причина:

Оконная функция ROW_NUMBER() работает с упорядоченным набором строк. PostgreSQL должен подготовить строки в порядке height DESC для узла WindowAgg.

Хотя условие rn <= 3 есть, это уже условие поверх результата оконной функции. Поэтому план сложнее, чем обычный LIMIT.


3. WindowAgg
------------

План:

WindowAgg
Run Condition: row_number() OVER (...) <= 3

WindowAgg считает ROW_NUMBER() по строкам, отсортированным по height DESC.

Run Condition показывает, что PostgreSQL оптимизировал выполнение и выпускает наружу только строки с row_number <= 3. Но оконная обработка все равно остается дополнительным шагом.


4. Subquery Scan
----------------

Внешний запрос читает результат подзапроса t. На выходе остаются 3 строки.


Сравнение вариантов запроса 45
------------------------------

Вариант 1:

ORDER BY height DESC LIMIT 3
Execution Time: 7.453 ms

Вариант 2:

ROW_NUMBER()
Execution Time: 10.461 ms

Первый вариант быстрее.

Причина:

- LIMIT позволяет использовать top-N heapsort;
- ROW_NUMBER() требует оконной функции WindowAgg;
- во втором варианте сортировка использует больше памяти: 3057kB против 25kB;
- оконный вариант сложнее для простой задачи "топ-3".

Практический вывод:

Для выбора трех самых высоких спортсменов лучше использовать ORDER BY + LIMIT.

ROW_NUMBER() стоит использовать, если нужно не просто top-3 по всей таблице, а, например:

- top-3 в каждом клубе;
- место спортсмена в рейтинге;
- дополнительные оконные вычисления.


Запрос 41. Разряды за 2024 год
==============================

Задача:

Нужно вывести id спортсмена, фамилию с инициалом, дату присвоения и название разряда для записей Rank за 2024 год.


Запрос 41, вариант 1. EXTRACT(YEAR FROM date)
---------------------------------------------

SQL:

SELECT a.athlete_id,
       a.last_name || ' ' || LEFT(a.first_name, 1) || '.' AS fio,
       r.assignment_date,
       rt.rank_title
FROM Athlete a
JOIN Rank r ON r.athlete_id = a.athlete_id
JOIN Rank_title rt ON rt.rank_title_id = r.rank_title_id
WHERE EXTRACT(YEAR FROM r.assignment_date) = 2024
ORDER BY a.athlete_id, r.assignment_date DESC;

Итог:

Execution Time: 22.865 ms
Planning Time: 0.342 ms
Результат: 3 строки
Buffers: shared hit=1286


1. Seq Scan on rank r
---------------------

План:

Seq Scan on rank r
Filter: EXTRACT(year FROM assignment_date) = '2024'::numeric
Rows Removed by Filter: 147609
actual rows=3

Это главный проблемный узел.

PostgreSQL прочитал всю таблицу Rank:

147612 строк.

Из них подошло только 3 строки. Остальные 147609 строк были отброшены фильтром.

Почему так произошло:

Условие применяет функцию EXTRACT к столбцу assignment_date. Для каждой строки PostgreSQL должен вычислить год из даты, а потом сравнить его с 2024.

Такое условие хуже для оптимизации, чем прямое сравнение даты с диапазоном.

Даже если есть обычный индекс по assignment_date, выражение EXTRACT(YEAR FROM assignment_date) обычно не позволяет использовать его как простой диапазонный поиск.


2. Seq Scan on athlete a
------------------------

План:

Seq Scan on athlete a
actual rows=36084

PostgreSQL прочитал всю таблицу Athlete и построил по ней хэш.

Это произошло потому, что оптимизатор ожидал около 738 строк из Rank, а не 3. Поэтому он решил, что выгодно построить хэш по Athlete и соединять через Hash Join.


3. Hash Join Rank + Athlete
---------------------------

План:

Hash Join
Hash Cond: r.athlete_id = a.athlete_id
actual rows=3

После фильтра по году осталось 3 записи Rank. Они соединяются со спортсменами.

Фактически итог маленький, но из-за оценки оптимизатора план прочитал всю Athlete.


4. Hash Join с Rank_title
-------------------------

План:

Hash Join
Hash Cond: r.rank_title_id = rt.rank_title_id

Rank_title маленькая таблица, поэтому PostgreSQL читает ее целиком и строит маленький хэш.


5. Sort
-------

План:

Sort Key: a.athlete_id, r.assignment_date DESC
Sort Method: quicksort
Memory: 25kB

Сортируются всего 3 итоговые строки, поэтому сортировка почти ничего не стоит.


Вывод по варианту 1
-------------------

Запрос работает правильно, но план неудачный для производительности:

- вся Rank прочитана ради 3 строк;
- для каждой строки Rank вычислялся EXTRACT;
- вся Athlete прочитана и захэширована;
- обычный индекс по assignment_date не был бы так полезен, как для диапазонного условия.


Запрос 41, вариант 2. Диапазон дат
----------------------------------

SQL:

SELECT a.athlete_id,
       a.last_name || ' ' || LEFT(a.first_name, 1) || '.' AS fio,
       r.assignment_date,
       rt.rank_title
FROM Athlete a
JOIN Rank r ON r.athlete_id = a.athlete_id
JOIN Rank_title rt ON rt.rank_title_id = r.rank_title_id
WHERE r.assignment_date >= '2024-01-01'
  AND r.assignment_date < '2025-01-01'
ORDER BY a.athlete_id, r.assignment_date DESC;

Итог:

Execution Time: 4.742 ms
Planning Time: 0.207 ms
Результат: 3 строки
Buffers: shared hit=810


1. Seq Scan on rank r
---------------------

План:

Seq Scan on rank r
Filter:
  assignment_date >= '2024-01-01'
  assignment_date < '2025-01-01'
Rows Removed by Filter: 147609
actual rows=3

PostgreSQL снова прочитал всю Rank. В этом конкретном плане индекс по assignment_date не использован. Вероятно, его нет или оптимизатор решил, что Seq Scan дешевле.

Но этот вариант все равно намного быстрее.

Причина:

Сравнить дату с двумя константами дешевле, чем вычислять EXTRACT(YEAR FROM date) для каждой строки.

В плане видно:

- EXTRACT-вариант сканировал Rank до 15.484 ms;
- диапазонный вариант сканировал Rank до 4.693 ms.

Разница большая, хотя оба варианта прочитали одинаковое количество строк.


2. Nested Loop Rank -> Athlete
------------------------------

План:

Nested Loop
Index Scan using athlete_pkey on athlete a
Index Searches: 3

После фильтра Rank осталось 3 строки. PostgreSQL выбрал точечный поиск спортсменов по первичному ключу.

Это эффективнее, чем читать всю Athlete.

В первом варианте PostgreSQL прочитал все 36084 строки Athlete. Во втором варианте он сделал только 3 индексных поиска.


3. Nested Loop с Rank_title
---------------------------

План:

Seq Scan on rank_title rt
loops=3

Для каждой из 3 строк PostgreSQL просматривает маленькую таблицу Rank_title.

Так как Rank_title содержит всего 14 строк, это дешево.


4. Sort
-------

План:

Sort
Sort Method: quicksort
Memory: 25kB

Сортируются 3 строки, стоимость минимальная.


Сравнение вариантов запроса 41
------------------------------

Вариант 1:

EXTRACT(YEAR FROM r.assignment_date) = 2024
Execution Time: 22.865 ms

Вариант 2:

r.assignment_date >= '2024-01-01'
AND r.assignment_date < '2025-01-01'
Execution Time: 4.742 ms

Второй вариант быстрее примерно в 4.8 раза.

Главные причины:

1. Диапазонное условие дешевле вычисляется.
2. Диапазонное условие лучше подходит для обычного индекса по дате.
3. Оптимизатор выбрал Nested Loop и 3 точечных Index Scan по athlete_pkey.
4. Первый вариант построил Hash Join с полной таблицей Athlete.

Практический вывод:

Для дат почти всегда лучше писать диапазоны:

assignment_date >= DATE '2024-01-01'
AND assignment_date < DATE '2025-01-01'

а не:

EXTRACT(YEAR FROM assignment_date) = 2024

Особенно если планируется индекс:

CREATE INDEX ON Rank(assignment_date);

Общий вывод
===========

Самый содержательный план - у запроса 48. В нем есть Hash Join, Hash Anti Join, HashAggregate и во втором варианте Recursive Union. Он хорошо показывает, как PostgreSQL выполняет NOT EXISTS и DISTINCT.

Самое наглядное сравнение - у запроса 45. Простой LIMIT позволяет использовать top-N heapsort, а ROW_NUMBER() добавляет оконную обработку и обычную сортировку.

Самое важное практическое сравнение - у запроса 41. Замена EXTRACT на диапазон дат уменьшила время с 22.865 ms до 4.742 ms. Это хороший пример того, почему функции от столбца в WHERE часто ухудшают планы, а диапазонные условия по датам обычно лучше.
