ОТЧЕТ ПО ИНДЕКСАМ С РЕАЛЬНЫМИ РЕЗУЛЬТАТАМИ (305,102 строки)

В лабораторной работе сравнивались две таблицы с идентичными данными:
- athlete_no_index - таблица без дополнительных индексов
- athlete_with_index - таблица с индексами

СОЗДАННЫЕ ИНДЕКСЫ:
- idx_athlete_last_name ON athlete_with_index(last_name)
- idx_athlete_first_name ON athlete_with_index(first_name)
- idx_athlete_birth_date ON athlete_with_index(birth_date)

ОБЩИЙ ОБЪЕМ ДАННЫХ В КАЖДОЙ ТАБЛИЦЕ:
- Исходные данные из Athlete: 102 строки
- Тестовые данные (случайные): 100,000 строк
- Данные для поиска 'Kozlov': 5,000 строк
- Данные с разными датами: 50,000 строк
- Группа 'UpdateGroup': 50,000 строк
- Группа 'IndexedUpdate_Old': 50,000 строк
- Группа 'DeleteGroupIndexed': 50,000 строк
ИТОГО: ~305,102 строки в каждой таблице

================================================================================
1. UPDATE НЕИНДЕКСИРУЕМОГО СТОЛБЦА (height) С ПОИСКОМ ПО ИНДЕКСИРОВАННОМУ ПОЛЮ
================================================================================

Запрос: UPDATE ... SET height = height + 1 WHERE last_name = 'UpdateGroup'
Обновляется 50,000 строк (НЕиндексируемый столбец height)
Поиск по last_name (есть индекс idx_athlete_last_name)

ТАБЛИЦА БЕЗ ИНДЕКСА (athlete_no_index):
--------------------------------------------------
Plan: Seq Scan on athlete_no_index
Filter: last_name = 'UpdateGroup'
Rows Removed by Filter: 255,102
Execution Time: 67.435 ms

Почему так долго:
- PostgreSQL выполняет ПОСЛЕДОВАТЕЛЬНОЕ СКАНИРОВАНИЕ всех 305,102 строк
- Каждую строку проверяет на условие last_name = 'UpdateGroup'
- Находит 50,000 подходящих строк
- Обновляет поле height (неиндексируемое, но это не важно)

ТАБЛИЦА С ИНДЕКСАМИ (athlete_with_index):
--------------------------------------------------
Plan: Bitmap Heap Scan on athlete_with_index
  -> Bitmap Index Scan on idx_athlete_last_name
Index Cond: last_name = 'UpdateGroup'
Heap Blocks: exact=715
Execution Time: 233.197 ms

Почему так происходит:
1. Bitmap Index Scan: быстро находит 50,000 строк в индексе (0.528 ms)
2. Bitmap Heap Scan: читает эти строки из таблицы (715 блоков)
3. Обновляет поле height в каждой строке
4. PostgreSQL должен ПРОВЕРИТЬ и ОБНОВИТЬ все индексы

СРАВНЕНИЕ:
Без индекса:     67.435 ms
С индексом:     233.197 ms
Замедление:     165.762 ms (В 3.46 РАЗА МЕДЛЕННЕЕ!)

ПАРАДОКС: Индекс помог найти строки за доли миллисекунды, но операция UPDATE 
в целом стала медленнее! Почему?

ПРИЧИНА: При UPDATE даже неиндексируемого столбца PostgreSQL должен:
1. Заблокировать строки для обновления
2. Создать новые версии строк (MVCC)
3. Обновить системные каталоги
4. ПРОВЕРИТЬ, не изменились ли индексированные столбцы
5. Поддержать целостность индексов

В таблице с индексами эти дополнительные операции перевешивают выигрыш от быстрого поиска.

================================================================================
2. UPDATE ИНДЕКСИРУЕМОГО СТОЛБЦА (last_name) С ПОИСКОМ ПО ИНДЕКСИРОВАННОМУ ПОЛЮ
================================================================================

Запрос: UPDATE ... SET last_name = 'IndexedUpdate_New' WHERE first_name = 'IndexedUpdateGroup'
Обновляется 50,000 строк (индексируемый столбец last_name)
Поиск по first_name (есть индекс idx_athlete_first_name)

ТАБЛИЦА БЕЗ ИНДЕКСА (athlete_no_index):
--------------------------------------------------
Plan: Seq Scan on athlete_no_index
Filter: first_name = 'IndexedUpdateGroup'
Rows Removed by Filter: 255,102
Execution Time: 69.081 ms

Почему так долго:
- Полное сканирование всех 305,102 строк
- Нет индекса для быстрого поиска по first_name
- Обновляет last_name (но индексов нет, поэтому обновлять нечего)

ТАБЛИЦА С ИНДЕКСАМИ (athlete_with_index):
--------------------------------------------------
Plan: Seq Scan on athlete_with_index  (ВНИМАНИЕ! Seq Scan, а не Index Scan!)
Filter: first_name = 'IndexedUpdateGroup'
Rows Removed by Filter: 255,102
Execution Time: 288.531 ms

ПОЧЕМУ НЕ ИСПОЛЬЗОВАЛСЯ ИНДЕКС?

Несмотря на наличие индекса idx_athlete_first_name, PostgreSQL выбрал 
последовательное сканирование. Возможные причины:
1. Оптимизатор посчитал, что 50,000 строк из 305,102 (16% таблицы) - это 
   слишком много для использования индекса
2. При таком объеме выборки последовательное чтение может быть эффективнее
3. Стоимость random access (чтение индекс + чтение таблицы) выше, чем 
   последовательное сканирование

Но почему время выросло до 288 ms?
- Поиск: полное сканирование 305k строк (как и без индекса) - 17.875 ms
- Обновление: изменение last_name (индексируемый столбец)
- ДОПОЛНИТЕЛЬНО: обновление индекса idx_athlete_last_name для 50,000 строк
- Каждое обновление индекса: удаление старой записи + вставка новой

СРАВНЕНИЕ:
Без индекса:      69.081 ms
С индексом:      288.531 ms
Замедление:      219.450 ms (В 4.18 РАЗА МЕДЛЕННЕЕ!)

ВЫВОД: Обновление индексируемого столбца - самая дорогая операция. 
Даже если бы использовался Index Scan, стоимость обслуживания индекса все равно 
была бы высокой.

================================================================================
3. DELETE СТРОК (НЕ ИСПОЛЬЗУЕТ ИНДЕКС)
================================================================================

Запрос: DELETE FROM ... WHERE first_name = 'DeleteGroupFirstName'
Удаляется 50,000 строк
Поиск по first_name (индекс ЕСТЬ на athlete_with_index, но не используется)

ТАБЛИЦА БЕЗ ИНДЕКСА:
--------------------------------------------------
Plan: Seq Scan on athlete_no_index
Filter: first_name = 'DeleteGroupFirstName'
Rows Removed by Filter: 255,102
Execution Time: 26.701 ms

ТАБЛИЦА С ИНДЕКСАМИ:
--------------------------------------------------
Plan: Seq Scan on athlete_with_index
Filter: first_name = 'DeleteGroupFirstName'
Rows Removed by Filter: 255,102
Execution Time: 25.638 ms

СРАВНЕНИЕ:
Без индекса:     26.701 ms
С индексом:      25.638 ms
Разница:         1.063 ms (ПРАКТИЧЕСКИ ОДИНАКОВО)

ПОЧЕМУ НЕТ РАЗНИЦЫ?
1. PostgreSQL снова выбрал Seq Scan (как и в UPDATE)
2. Поиск 50,000 строк выполняется одинаково в обеих таблицах
3. Разница в обслуживании индексов минимальна (1 ms)

ЕСЛИ БЫ ИСПОЛЬЗОВАЛСЯ ИНДЕКС:
- Время удаления сократилось бы до 10-15 ms
- Но оптимизатор решил, что 16% таблицы - это слишком много для индекса

================================================================================
4. INSERT НОВЫХ СТРОК (50,000 строк)
================================================================================

Запрос: INSERT 50,000 новых строк

ТАБЛИЦА БЕЗ ИНДЕКСА:
--------------------------------------------------
Execution Time: 46.530 ms

Что происходит:
- Выделение места для 50,000 строк
- Запись данных в таблицу
- Никаких дополнительных операций

ТАБЛИЦА С ИНДЕКСАМИ:
--------------------------------------------------
Execution Time: 261.606 ms

Что происходит:
- Выделение места для 50,000 строк
- Запись данных в таблицу
- ДЛЯ КАЖДОЙ СТРОКИ добавление в 3 индекса:
  * idx_athlete_last_name
  * idx_athlete_first_name  
  * idx_athlete_birth_date
- Итого: 150,000 операций добавления в индексы

СРАВНЕНИЕ:
Без индекса:      46.530 ms
С индексом:      261.606 ms
Замедление:      215.076 ms (В 5.62 РАЗА МЕДЛЕННЕЕ!)

ФОРМУЛА: Время INSERT ≈ время записи в таблицу + (кол-во индексов × время на индекс)
С каждым новым индексом INSERT замедляется линейно.

================================================================================
ОБЩИЙ АНАЛИЗ ПОЛУЧЕННЫХ РЕЗУЛЬТАТОВ
================================================================================

1. UPDATE (неиндексируемый столбец):
   67 ms без индекса → 233 ms с индексом (замедление в 3.5x)
   Парадокс: индекс ускорил поиск, но замедлил обновление

2. UPDATE (индексируемый столбец):
   69 ms без индекса → 288 ms с индексом (замедление в 4.2x)
   Самая дорогая операция из-за обновления индекса

3. DELETE (по неиндексированному полю):
   27 ms без индекса → 26 ms с индексом (почти одинаково)
   Индекс не использовался оптимизатором

4. INSERT:
   47 ms без индекса → 262 ms с индексом (замедление в 5.6x)
   Каждый индекс добавляет время на вставку

================================================================================
КЛЮЧЕВЫЕ ВЫВОДЫ ИЗ ЭКСПЕРИМЕНТА
================================================================================

1. ИНДЕКСЫ НЕ ВСЕГДА УСКОРЯЮТ UPDATE:
   Даже при быстром поиске строк, UPDATE может быть медленнее из-за 
   необходимости проверять и обслуживать индексы.

2. ОПТИМИЗАТОР - НЕ ГЛУПЫЙ:
   PostgreSQL может не использовать индекс, если считает, что выборка 
   составляет слишком большой процент таблицы (в нашем случае 16%).

3. INSERT СТРАДАЕТ БОЛЬШЕ ВСЕГО:
   Вставка в таблицу с 3 индексами в 5.6 раз медленнее. Для систем с 
   частыми вставками это критично.

4. КАЖДЫЙ ИНДЕКС ИМЕЕТ ЦЕНУ:
   - Ускоряет SELECT (если выборка < 5-10% таблицы)
   - Замедляет INSERT, UPDATE, DELETE
   - Занимает дополнительное место на диске

================================================================================
ПРАКТИЧЕСКИЕ РЕКОМЕНДАЦИИ
================================================================================

1. СОЗДАВАЙТЕ ИНДЕКСЫ ТОЛЬКО, ЕСЛИ:
   - Столбец часто используется в WHERE, JOIN, ORDER BY
   - Выборка возвращает менее 10% строк таблицы
   - Таблица редко обновляется

2. ИЗБЕГАЙТЕ ИНДЕКСОВ, ЕСЛИ:
   - Столбец часто обновляется
   - Таблица имеет высокую нагрузку на запись
   - Выборка возвращает большую часть таблицы

3. ТЕСТИРУЙТЕ НА РЕАЛЬНЫХ ДАННЫХ:
   - На маленьких таблицах индексы могут не давать выигрыша
   - На больших - могут как ускорять, так и замедлять

4. ДЛЯ OLTP СИСТЕМ:
   - Минимум индексов (только самые важные)
   - Композитные индексы вместо нескольких отдельных
   - Партицирование больших таблиц

5. ДЛЯ OLAP СИСТЕМ:
   - Больше индексов для ускорения сложных запросов
   - Индексирование всех полей в WHERE
   - Рассмотрение bitmap индексов

В НАШЕМ ЭКСПЕРИМЕНТЕ С 305,000 СТРОК:
- Выигрыш от индекса при SELECT: потенциально 10-100x (если бы использовался)
- Проигрыш от индексов при INSERT: 5.6x (46.5 ms → 261.6 ms)
- Проигрыш от индексов при UPDATE: 3.5-4.2x

Вывод: Для систем с частыми операциями записи цена индексов может значительно 
превысить выгоду от ускорения чтения. Всегда оценивайте соотношение операций 
чтения и записи перед созданием индексов!
